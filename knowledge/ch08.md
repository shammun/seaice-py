## 1. Concepts (what the chapter teaches, in our words)

- The chapter is **three applications** of the ch2–ch7 pipeline, not new image processing: a shipborne ice-concentration
  camera (§8.1), numerical characterisation of a real ice field for a DEM simulator (§8.2), and the floe size
  distribution of a helicopter frame (§8.3). The unnumbered intro (pp. 175–176) lists six motivations; only (4),
  synthetic ice-field generation, is actually implemented — by §8.2.1 + Appendix B.
- **§8.1** An oblique 4-lens camera on IB *Frej* (OATRC'15), 1 frame / 10 s, is **linearly rectified** from four
  checkerboard corners (**Appendix A.1.2 → ch10**, deliberately *not* written here), then ice pixels are extracted
  **twice**: global Otsu (§3.1) and k-means with **k = 3** (§3.2). The three clusters read water / **wet ice** (rubble,
  young ice, melt ponds) / dry ice, and **both the grey and the white cluster count as ice** — which is why the
  k-means series of Fig. 8.5 sits systematically *above* Otsu's. Ice concentration = ice px / total px.
- The book's claim "k = 2 k-means ≈ Otsu" (p. 179) is a statement about the *threshold*, and it is only interesting on a
  histogram with no empty band — on a two-tone image every threshold in the gap gives the same mask (see lesson 4).
- **§8.2** Figure 8.8 is undistorted, so "**Algorithms 3, 4 and 5 are carried out directly**" (p. 182) — ch07's whole
  pipeline with no rectification and no tiling. Piece size = pixel count, colour-coded by ch07's **Eq. (7.6)**.
- **§8.2.1 numerical modelling**: MIZ floes are "generally rounded", so for a simulator each **floe is replaced by its
  convex hull** (`convhull(x, y, 'simplify', true)`; the book says "bounding minimum-area polygon", which is only true
  for the *convex* minimum) and each **brash piece by an area-equivalent disk**, `r = sqrt(A/π)`, `p = 2πr` (C2).
- Every polygonized floe carries an **overlap flag**: the serial numbers of the floes and brash pieces it intersects,
  for a 3-D DEM simulator's collision resolution. Floe–floe and floe–brash overlap is tested by **boundary crossing**
  (`polyxpoly`, C4); brash–brash by the pure circle test `‖c_i − c_j‖ < r_i + r_j` (C3).
- The results are stored in the **Appendix B `IceImage` structure** (pp. 221–225) — `Param` / `Field` /
  `Floe(i).{Area, Center, Perimeter, Pixels, Polygon{Vertices, Area, Center, Perimeter, Intersect}}` /
  `Brash(i).{…, Circle{Radius, Perimeter, Intersect}}`. Coordinates are **1-based `[x, y] = [column, row]`** and
  `Polygon.Vertices` is an **open** ring (the closing vertex is deleted).
- The Appendix-B **FSD** (C5) is 51 triplets `[int_min, int_max, num]` built from `hist(areas, min_x:inter:max_x)` —
  `hist` on **bin centres**, so the printed interval labels do *not* describe the counts (erratum E8).
- **§8.3, Eq. (8.1)** `L_i = sqrt(4A_i/π)` — the "mean clipper diameter" (MCD). Both words are wrong: it is *caliper*
  (Rothrock & Thorndike 1984), and the formula is the **area-equivalent circle diameter**, not a support-function
  diameter (erratum E5). Pixels become metres through the single literal `length_over_Pixel = 1.1794` m/px, which the
  book never prints (it says IB *Oden*'s known length was used).
- **Eq. (8.2)** `N_c(L) = N(≥L)/N_total`, evaluated at **every observed** `L_i`, so `N_c` runs from 1 down to `1/N` and
  ties give repeated values (the vertical marker stacks of Fig. 8.21). Despite the text ("number of floes per unit
  area"), there is **no area normalisation**.
- **Eq. (8.3)** `N_c(L) ∝ L^{-α}`, fitted as `ε₁ L^{-ε₂}` with `lsqcurvefit` on the **untransformed** pairs — *not*,
  as the text says, as a straight line on a log-log plot (that gives α = 1.8697; the code gives **1.37036**,
  erratum E2). No goodness-of-fit statistic is computed anywhere in the chapter; `resnorm`, `residual`, `exitflag`,
  `output` and `jacobian` are all requested and discarded.
- Two further models exist only in the code: the **upper-truncated power law** `ε₁(L^{-ε₂} − ε₃^{-ε₂})` (C9) and the
  **Weibull survival function** `exp(−(L/ε₂)^{ε₁})` (C10). Their call site is **commented out**.
- Figs. 8.19/8.20's colour bar is `jet(30)` with `caxis([centers(1) centers(30)]) = [1, 30]`: every MCD above the 30th
  histogram centre is painted in the **last** colour, which is what "≥30 [m]" means. The colour index is the **nearest
  histogram centre**, `[~, index] = min(abs(MCD(i) − centers))` (C11) — not a `hist` bin assignment.
- Fig. 8.15 is the **difference of two floe-size histograms** (polygonized − identified) showing the error the shape
  simplification introduces; `main_WL_new.m`'s `count_error` (C1) is a *different* quantity, `P_k − R_{k+1}`, with a
  deliberate one-bin shift because polygonization enlarges MCD by roughly one 1-m bin.

## 4. MATLAB→Python lessons learned (new pitfalls; each is a row in `function_map.md`)

1. **MATLAB grows an array on an out-of-range assignment instead of erroring, so a result's *size* is
   data-dependent.** `plot_color_bar_and_floe.m:79` writes `rgbImage(y(j), x(j), :) = …` into a variable that starts
   as `[]`, so the array ends up `max(y) × max(x) × 3` — **not** the image size. On the shipped field both maxima are
   attained (627×1114), so that run alone cannot tell "grown" from "pre-allocated"; the review forced a fixture that
   can (`Floe(1:50)` → **627×1096×3**, the floes inside `x ≤ 900, y ≤ 500` → **489×865×3**, both byte-identical).
   **Never pre-allocate where the original grows** — and if you offer a pre-allocating override, give it its own test.
2. **`if x ~= NaN` is `if ~isempty(x)`.** A comparison with NaN is false for *every* element, so `if` sees an all-false
   (or empty) array and the test degenerates to "did the array have elements". `sea_ice_model.m` uses this idiom four
   times, so a floe **entirely inside** another is reported as **non-overlapping** — a genuine limitation of the
   published algorithm, reproduced literally and pinned in both directions (`strict_containment=True` sees the
   containment the shipped form misses). MATLAB confirmed all three branches (`[1 2 3]` taken, `[]` not, `[1 NaN]`
   taken) and that `polyxpoly` on a strictly nested square returns empty. `ch9/model_ice_model.m` carries the same
   idiom — do not "fix" it there either.
3. **`a:step:b` with a non-integer step does not reach `b`, and MATLAB's colon is more accurate than
   `start + k·step`.** `t = 0:0.05:6.28` is **126** points ending at **6.25**, so every brash "circle" in the book's
   own results is an open 125-gon with a 0.033 rad gap (erratum E10). Pin **both** the element count and the last
   value; 30 of the 126 angles are ≤ 1 ulp off (max 8.9e-16) and the difference was proven inert (0 px on `bw_brash`).
   Integer colons are bit-exact — but choose a fixture whose `(b−a)/d` is **not** integral, or the truncation logic is
   never exercised (review N4: `21:79:3971` proves nothing, the real line `21:79:3979` gives 51 elements ending 3971).
4. **A degenerate fixture can make an agreement inevitable — the §8.1 k = 2 ≈ Otsu case.** The first fixture was a
   two-tone frame whose histogram has a 150-level empty gap, so *every* threshold in the gap gives the same mask. It
   was rebuilt as a ramp covering **every** level 55…205: Otsu picks **116**, k-means' centre midpoint is **116.2525**
   — different numbers — and the masks still agree on **100.00 %**, with 11 px at level 116 and 30 at 117 so that a
   one-level move would break it. Same family as ch07's saturating-agreement lesson, applied to a claim the book makes
   in *words* rather than in a figure.
5. **Reach for the authors' own deterministic routine over a library equivalent with an RNG when both exist**
   (rule 4, review S6). §8.1 called ch06's seeded `kmeans_lloyd` (`approx`) where ch03's port of the authors' own
   `ch3/kmeans.m` (`kmeans_gray`, deterministic, `exact`) *is* the §3.2 routine the book names. `impl='authors'` is now
   the default; `'lloyd'` is opt-in and seed-dependent (seeds 0/1/7 give three different k = 3 centre triplets, seed 1
   happening to land on the authors' answer). The two branches are pinned with numbers that **differ**, so a test in
   which `impl` silently routed both to the same routine would fail.
6. **A shipped `.mat` of the authors' own results is the strongest reference available.** `MCD_results.mat` is one
   variable (`Raw_MCD`, 1×2888) and `IceImage_290915_2_jpg.0000179.mat` is the complete Appendix-B structure, so the
   chapter could **re-run the authors' code on the authors' own stored inputs** and compare **structure to structure**:
   2888 floes + 3452 brash, `Area ≤ 1.8e-12`, hull vertex **sets** 2888/2888, all **3992** overlap-list entries equal
   as sets, `Radius`/`Perimeter` 0.0. That is L3 evidence no synthetic fixture can match.
7. **An unidentifiable parameter makes "parity" meaningless along that direction** (D2). In
   `ε₁(L^{-ε₂} − ε₃^{-ε₂})` the objective is flat in `ε₃` (as `ε₃ → ∞` the model degenerates to the plain power law),
   so Python lands at 9.94e5 where MATLAB stops at 766. **Measure the objective, not the parameter**, report *both*
   minima (Python's is better in 2 of 3 fixtures, worse by 1.4e-4 relative in the third, and MATLAB stops early only
   because the file sets `TolFun 1e-5`), and prove the claim with a refit test: fixing `ε₃` anywhere in [766, 1e6]
   changes the residual sum by < 1e-6.
8. **A toolbox optimiser's defaults are discoverable — capture them from MATLAB itself.** A one-off
   `optimoptions('lsqcurvefit')` probe (`reference/ch08/probe.mat`) confirmed `Algorithm =
   'trust-region-reflective'`, `FunctionTolerance = StepTolerance = 1e-6`, `MaxIterations = 400`,
   `MaxFunctionEvaluations = '100*numberOfVariables'` — exactly the table now hard-coded in `core/fitting.py`.
   Do not assume them from documentation, and record where the probe came from (review N10).
9. **`convhull`'s vertex order is not reproducible** (the ch06 `polybool` lesson again, now for a *different* routine):
   the start vertex and traversal direction matched on only **105 of 227** floes. Contract on the **vertex set** and
   the **rasterised mask** — both 0 px/identical — and label the `Vertices` field `near`, not `exact`.
10. **A fixture that is square cannot catch a (row,col) ↔ (x,y) transposition** (review S1). All four
    `sea_ice_model`/Appendix-B fixtures were square, so swapping `NumPix_x`/`NumPix_y` left every assertion true. One
    fixture is now **80 × 137**; the swap was then actually **performed, observed to fail** (`PixScale_x` 0.625 vs
    MATLAB's 50/137 = 0.36496350364963503) **and reverted** (the module's md5 is unchanged). Choose fixture *shapes*
    that can fail, and prove the fixture discriminates by introducing the bug.
11. **The HG1 patch ch07 predicted was needed, verbatim.** `color_hist.m` and `color_hist_comparison.m` carry the same
    `get(h,'Children')` → `'Faces'` → `'FaceVertexCData'` block that errors in R2025a; the recipe from
    `outputs/ch07/verify/patches.json` transferred unchanged. Total patch set for the chapter: **122 edits**, all
    graphics or output plumbing, each stored beside the removed source line in `reference/ch08/patches.json`.
12. **A shipped file can be un-runnable.** `fitting_iceFloes_distribution.m:57` —
    `legend(gca,{'Observed data','Power law fitting''},'Box','on')` — is a **syntax error**, not a rendering quirk;
    MATLAB's own parser message is stored in `fit.mat` as `legend_err`. The script cannot have produced Fig. 8.21 in
    the form it ships. Capture the refusal as evidence, delete the one line in the scratch copy, record it (erratum E1).
13. **A speed-up must be proven inert on the run that is pinned, and the two measurements must not be merged**
    (review N8). D5 is now (a) flag-by-flag equivalence on a 60 + 60 subset (identical `Intersect` lists, 0 px in every
    combination) and (b) the prefilter demonstrably skipping work on the full runs (900 of 160 262 pairs; 13 466 of
    28 276 408) — (b) being the stronger evidence because those defaults are exactly the configuration compared
    against MATLAB's literal loop. The equivalence is also an *argument*: a common point of two polylines lies inside
    both AABBs, so disjoint AABBs cannot cross.
14. **Read a struct field the way MATLAB reads it — column-major.** 4 of 3452 shipped brash pieces have a **2×2**
    `Center`, and `c(1), c(2)` takes column-major elements `(x₁, x₂)`, not the first row. The `center2x2` fixture was
    built so the two candidate readings reach **different** brash pieces, and the test asserts MATLAB's choice (`{2}`)
    *and* the absence of the other (`3 not in …`). The related D4 (MATLAB's `cat(1, brash.Center)` is **4×2 for 3
    pieces**) is now asserted from the reference variable instead of resting on a human loading the `.mat`.
15. **The shipped labels of a histogram can be wrong while its counts are right** (E8). `SeaIce_Image_Structure.m:98`
    passes `min_x:inter:max_x` to `hist`, which reads them as **centres**: the first triplet is labelled `[21, 99]` but
    counts everything ≤ 60.5. Reproducing through `core.histogram.hist` gives **51/51** triplets; re-counting from the
    printed labels gives **1861 instead of 1411** and disagrees in **24 of 51** intervals. Verdict recorded in both
    directions — the counts are the authority.

## 8. Open questions / things to revisit

1. **§8.1 has no code and no data (O1).** Every printed §8.1 number stays `unverified`; only the *method* is verified
   (L1 on synthetic frames, its constituents `exact` from ch03). The Appendix-A.1.2 rectifier is ch10's.
2. **§8.2's printed 498 floes / 201 brash and 76.73/0.46/9.05/13.76 % do not reproduce (O2)** and the authors'
   parameter set is not printed anywhere. Fig. 8.10's tick pre-image corroborates the gap from the book's side. A
   parameter search was forbidden and was not performed; if ch09 or a later revision wants to close this, it must say
   so explicitly and report the search.
3. **Fig. 8.18 does not ship (O3)** — the §8.3 pipeline cannot be re-run from the image, only from the structure. The
   Fig. 8.19 comparison therefore uses the *reconstruction* from `Floe.Pixels`, labelled as such.
4. **The analysis's 0.9045 NCC for Fig. 8.19 was not reproduced as a raw correlation (O4)**: best-of-~6000-crops gives
   **0.8187** raw, rising to 0.9312 under a 1.2 px Gaussian. The raw figure is the one the report stands behind.
5. **`resnorm`/`exitflag` for the two orphan fit files needed inline repeats of their own `lsqcurvefit` calls (O5)**,
   because the files return only `eta`. The repeats are character-identical and are *additional probes*, not patches;
   the compared `eta` values come from the verbatim files.
6. **One new warning**: `RuntimeWarning: invalid value encountered in power` inside `core.fitting.weibull_survival` —
   the trust-region solver evaluates a trial `p[1] < 0`, the step is rejected, and the answer still lands within
   1.4e-4 relative of MATLAB's. Cosmetic, but it marks the one place where the port and MATLAB could diverge on a
   *rejected* trial point.
7. **`three_fitting_method_and_plotting.m`'s only call site is commented out and
   `PowerLaw_fitting_method_and_plotting.m` has no caller anywhere in `MATLAB_ROOT`.** Both are ported and verified;
   neither is wired into a default driver. If ch09 wants distribution fits, reuse `core.fitting`, not these scripts.
8. **The `Vertices` order residual is irreducible** (`convhull`'s start vertex/direction, 105 of 227 matched). If a
   later chapter needs an order-sensitive polygon consumer, feed it MATLAB's own vertex list or re-parameterise and
   measure the sensitivity, as ch06 did for `polybool`.
