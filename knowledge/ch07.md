## 1. Concepts (what the chapter teaches, in our words)

- The chapter starts where ch6's Algorithm 1 stops: the GVF-snake output is a **binary** segmentation, so all of
  §7.1 is a **binary** operation on it — enhance the shapes, then identify and classify the pieces (p. 145).
- **§7.1.1 morphological cleaning = closing then opening** with the same SE. Closing seals narrow cracks and small
  holes, opening breaks thin connections and deletes protrusions that cannot contain the SE (Fig. 7.2, a printed
  13×23 matrix with a 2×2 square SE: 111 → 115 (close) → 104 (open) → 108 (clean)).
- **§7.1.2 connected-component extraction, Eq. (7.1)** `X_k = (X_{k−1} ⊕ B) ∩ A`, `X_0 = {p}` — geodesic dilation of
  a seed, stopped at the fixed point. `B` = 3×3 square ⇒ 8-connectivity (Fig. 7.3, done at the 8th block); `B` = cross
  ⇒ 4-connectivity (Fig. 7.4, 7 blocks). It is `bwlabel`'s component containing the seed, computed by iteration.
- **§7.1.3.1 hole filling by the same recursion on `A^c`, Eq. (7.2)** (Fig. 7.5). Two failure modes are printed: with
  the cross SE only the hole containing the seed is filled (Fig. 7.6), and with the 3×3 square SE the recursion escapes
  through an 8-connection and floods the whole background (Fig. 7.7). Its real weakness is that the seed must be known
  to lie inside a hole — "difficult to automatically fulfil".
- **§7.1.3.2 reconstruction-based filling is automatic**: border marker **Eq. (7.3)** `F_m = 1 − F` on the border and 0
  inside, filled image **Eq. (7.4)** `H = [R^D_{F^c}(F_m)]^c` (Fig. 7.8). This *is* `imfill(·,'holes')`.
- **§7.1.4 Algorithm 2 (ice shape enhancement)**: label the segmentation, sort the pieces **small → large**, clean and
  fill each in that order, superimpose into a fresh label image. The sort is not cosmetic — "otherwise, the smaller ice
  piece contained in a larger ice floe may not be removed" (p. 151); a later, larger piece overwrites the earlier ones.
- **Eq. (7.5)** adapts the cleaning SE to the piece: `r = r1 (=1)` if `size_ice < size_th (=50)`, else `r2 (=2)`.
  `strel('disk',1)` is the 4-connected **cross** (5 px), not a 3×3 square — opening a rectangle with it removes the
  corners, so an identified area is not the labelled area.
- **Eq. (7.6)** size-codes each piece for display: `Color = C1(1 − e^{−area/C2})`, `C1 = 10⁴`, `C2 = 10³`, truncated by
  `fix`. Its inverse `−round(C2·log(1 − c/C1))` labels the colour bar — those tick integers are printed in six figures.
- **§7.2.1 ice pixel extraction**: Otsu gives "light ice" only (which is *wanted* — under-detection leaves the holes the
  §6.3.3 distance-transform initialisation needs), k-means with ≥ 3 clusters gives all ice, and "dark ice" = k-means −
  Otsu (Figs. 7.10(b)–(d)).
- **§7.2.2 Algorithm 3 (sea ice edge detection)**: run Algorithm 1 on the light and dark layers separately and label the
  result **differently** — `SEGMENTATION = 1·light + 0.5·dark` — because a connected light/dark pair could not otherwise
  be separated (Fig. 7.11). This is exactly `seaice_kmean_GVF_forenhancement.m`, ported in ch06.
- **§7.2.3 Algorithm 4**: feed light **and** dark pieces into Algorithm 2 as *one* input; enhancing the layers
  independently would produce overlapping identifications.
- **§7.2.4 Algorithm 5 (types + FSD)**: pieces ≥ `T_floe` are **floes**, smaller ones **brash** ("fragments not more
  than 2 m across"), the remaining ice pixels are **slush**, and `PIXEL_seaice = IDENTIFICATION ∪ ICE` — the ice mask
  must be *updated after* enhancement, because cleaning turns some water pixels into ice. Residue ice (the snake
  boundaries between merged floes, Fig. 7.16) is counted as slush but reported separately.
- **§7.3.1 large distorted images**: process **overlapping sub-images** (Algorithm 6, the overlap avoiding the §6.5.3
  border effect), then orthorectify with **nearest-neighbour** interpolation — the pixel values are *categories*, so an
  averaging interpolant would invent a class. Order matters: rectify **after Algorithm 3, before Algorithm 4**.
- **§7.3.2 sensitivity**: snake iterations 1 → 122 at GVF 500 (Fig. 7.24) and GVF iterations 1 → 1500 at snake 100
  (Fig. 7.27). Too few snake iterations ⇒ the initial contours over-segment and Algorithm 4 then merges them into
  *under*-segmentation; too few GVF iterations ⇒ a small capture range ⇒ over-segmentation. Brash boundaries are weaker,
  so the brash curves oscillate more. The GVF iteration count should scale with object size.

## 4. MATLAB→Python lessons learned (new pitfalls; each is a row in `function_map.md`)

1. **A function documented "IM2 has the same class as IM" must do its arithmetic in that class — including the float
   branch.** `imcomplement`'s float fallback was `1.0 - img.astype(np.float64)`, which silently promoted `single` to
   `double`. Because `imfill.m` complements **twice** around the reconstruction, a `single` image round-trips through
   `1 − (1 − x)`: MATLAB does it in single (`imcomplement(single(1e-8))` is exactly `1`,
   `imcomplement(imcomplement(single(0.1)))` = `0.100000024`), the port did it in float64 → **2 of 25 elements differ,
   max 2.2351742e-08**. Latent in ch07 (which passes `double`) and would have bitten ch08/ch09 through `bwdist`'s
   `single`. The same commit fixed `uint32`/`uint64`, which fell through to the float branch
   (`imcomplement(uint32([0 1 2]))` returned `float64 [1, 0, −1]`). This is the same family as ch06's
   promote-round-once and ch05's `imimposemin` "arithmetic in the input class" rules — now stated as a **general rule**.
2. **`eps(x)` is the positive spacing at `|x|`, which is not `nextafter`.** `hist.m` line 145 writes
   `edgesc = edges + eps(edges)`; on a negative edge whose magnitude is an exact power of two `eps` steps 2⁻⁵² while
   `np.nextafter(e, inf)` steps 2⁻⁵³ — a factor of two, and it flips a bin. Correct form: `edges + abs(np.spacing(edges))`.
   Verified bit-exact against MATLAB's own `eps([−1 −2 −0.5 1 2 0 −3])`, and pinned by a constructed fixture
   (`y = −2 + eps(−2)/2`, centres `[−3 −1 1]`: MATLAB and the port `[1 0 0]`, a `nextafter` port `[0 1 0]`).
3. **MATLAB `hist` uses bin CENTRES; `np.histogram` uses edges** — and the outer bins of the explicit-centres form are
   *unbounded*, so values outside the centre range are counted, not dropped. The first comparison edge is `−Inf`, so
   `hist` counts `−Inf` in the first bin and `+Inf` in the last: a "drop non-finite values" filter is wrong (the port
   had one for `−Inf` only). The non-finite guard only excludes them from `min`/`max`, and when *every* value is
   non-finite MATLAB sets `miny = maxy = 0`.
4. **A cited measurement must name its input.** The port's "1232 pieces / 433 floes / 290 brash / 84 border-touching"
   were measured on the *port's own* Algorithm-3 output; MATLAB's own segmentation gives **1211 / 433 / 274 / 106**.
   Both are true and neither is wrong — but only the second pair is a parity number, and a report that mixes them
   cannot be audited. Every number in `reports/ch07_verification.md` now says which segmentation it came from.
5. **Beware an agreement that a saturating function makes inevitable.** The port's snake = 1 run reproduced Fig.
   7.26(a)'s printed colour-bar ticks byte for byte — at two different downscalings that identify 319/260 and 393/336
   pieces. Eq. (7.6)'s `fix(10⁴(1 − e^{−A/10³}))` is **9997 for every A ≥ 8112**, so *any* run with a 2-px smallest and
   ≥ 8112-px largest piece prints that list. Four of the eleven printed tick lists are saturated and constrain nothing;
   the other seven pin the largest area to a band of 1–19 px. **Before recording an exact match as parity, ask what
   fraction of the input space would produce it.** (What *is* verified is the arithmetic: the `(min colour, step)` pair
   reproducing each printed list is unique, so 7–9 integers come out of 2 degrees of freedom.)
6. **A test whose fixtures cannot distinguish the fix from the bug is not a test.** The `eps(edges)` fix would have
   survived a revert to `nextafter` with the suite green — none of the 16 committed `hist` cases had an internal edge at
   a negative power of two. The discriminating fixture had to be *constructed*, and the test now also computes the wrong
   variant explicitly to prove it discriminates. Same rule in the other direction for the M1 defect: the test
   monkey-patches the old `1.0 - img.astype(np.float64)` back in and asserts it **fails** against MATLAB.
7. **`imfill` is not `binary_fill_holes`.** Measured: `scipy.ndimage.binary_fill_holes` equals MATLAB on every logical
   **conn-4** case but differs for conn 8 (3 of 13 logical cases) and *never* reproduces a non-logical input — wrong
   values for `uint8` 0/255 and wrong values **and class** for grayscale/`int16`/`±Inf`. ch7 passes a **double**, so the
   library call would have been wrong at the very place the analysis flagged (R2), and the class it returns is seen by
   `bwlabel`, `imclose` and `out(pp) = t` downstream.
8. **The book has a confirmed erratum at Fig. 7.7(e) `X8`**: the printed block has 53 object pixels, MATLAB running the
   original recursion gives **55** — the two cells at 1-based (8,9) and (9,9) are forced by `X7` and are set in the
   printed `X9 = X10 = A^c`. Keep both (`FIG_7_7_STEPS` = the recursion, `FIG_7_7_STEPS_BOOK` = as printed,
   `FIG_7_7_X8_TYPO` = the two cells) and let **MATLAB adjudicate**, not argument.
9. **Byte-identical code does not mean byte-identical data.** All 23 `.m` in `ch7/Sea_Ice_Floe_Identification/` are
   byte-identical to ch6's, but the shipped `sea_ice_test.jpg` is the *same photograph re-encoded*: **84.13 %** of
   samples differ (max |Δ| 43). `graythresh` is 162/255 on both, yet `bwlabel(bw,4)` gives **215** components here
   against ch6's **231**, and the k-means stage ch06 measured as **0 px** now differs on 510 px (0.125 %) with sorted
   centres 1.04 gray levels apart. **Check the data as well as the code before inheriting a previous chapter's numbers**,
   and make `load_image` resolve to the chapter's own copy (md5 `54e56aa8…` vs ch6's `fca33143…`).
10. **Old FEX/HG1 code will not run in a current MATLAB.** `ice_shape_enhancement.m` l. 214–224 uses HG1 handle
    graphics (`get(h,'Children')` → `'Faces'` → `'FaceVertexCData'`); in R2025a `get(barHandle,'Children')` returns an
    empty `GraphicsPlaceholder` and the next `get` errors, so the **chapter's central file has no reference until it is
    patched**. The patch removed only graphics statements (every quantity they consume is still computed and saved) and
    is recorded verbatim in `outputs/ch07/verify/patches.json`. `color_hist.m` and `color_hist_comparison.m` carry the
    same block → **ch08 will need the same patch** (this is the ch06 `minboundrect`/`convhull({'Qt'})` lesson again).
11. **MATLAB's `sort` is stable and the tie order decides which label survives.** `[A, ind] = sort([4 4 6 4 1 6 1 9 4 6
    1 2])` → `ind = [5 7 11 12 1 2 4 9 3 6 10 8]` = `np.argsort(kind='stable')`, verified end to end on deliberate
    6-way/4-way ties and on the 1211 real pieces. Algorithm 2's superimposition order *is* this permutation.
12. **A whole-image scratch array per piece can be cropped — but prove it against MATLAB, not against yourself.** The
    M-file allocates `b = zeros(size(out))` per piece; the port runs the same four operations on a bounding box padded
    by `4r + 6` and clipped to the image (**1.6 s vs 243.7 s** on 1211 pieces). Because `imclose` pre-pads with 0 (ch04),
    the equivalence is not automatic: it was re-measured against **MATLAB** on the real image (106 border-touching
    pieces) and on a purpose-built `border_notch` fixture where every piece touches a border and carries a notch cut in
    from it. 0 px in both modes.
13. **The book's `≥` vs the code's `>` is a real 5-piece difference.** p. 160 says "sizes equal to or larger than
    `T_floe`"; the shipped code writes `if area0 > min_floe` / `elseif area0 > min_brash`, and with `min_brash = 1`
    every 1-pixel piece is dropped from FLOE *and* BRASH. Measured: **433/290 (code)** vs **436/289 (book)** — 3 pieces
    of exactly 40 px move up, 2 pieces of 1 px reappear. Both forms have MATLAB references (the reference run uses
    `min_floe = 39`, `min_brash = 0`, which for integer areas *is* the `≥` form). Default = the code;
    `ice_types_classification`, which *is* the pseudocode, defaults to the book.
14. **`strel('disk', 1)` is the 4-connected cross (5 px), `strel('disk', 2)` is 13 px in 5×5.** That is what Eq. (7.5)
    applies, so opening a solid rectangle removes its four corners and the raw areas 1, 2, 20, 39, 40, 49, 50, 51 of the
    `thresholds` fixture become 35, 36, 38, 45 after cleaning. A "3×3 square" reading would have changed every count.
15. **`regionprops` in the `regionprops(L == i, …)` call form can return more than one component.** MATLAB
    `cat(1, cen.Centroid)` appends *k* centroids if a later, larger piece splits an earlier label; the port took
    `props[0]`. A 700-fixture search found **zero** splits (a later piece can only grow into its own concavities), but
    the assumption is now explicit in the code rather than implicit.

## 8. Open questions / things to revisit

1. **Figs. 7.1, 7.9 and 7.10–7.21 are `unverified` as figures and as numbers** (verification Open item 6). The 155×125,
   205×263 and aerial source images are not shipped and no `.m` produces them. 154/189, 2511/2624 and the eight
   coverage percentages need the authors' images; not a port failure.
2. **Algorithm 6 / §7.3.1.1 has no code and no fixed parameters** (Open item 1). The book gives neither the sub-image
   size, nor the overlap, nor the stitching rule; `tile`, `overlap` and `merge` are parameters and only the structural
   properties are proved (700 configurations partition the image exactly once).
3. **§7.3.2 is `unverified` by construction** (Open item 5): the book prints axis ranges and colour-bar ticks, no
   counts, and the tick agreement at snake = 1 is a **saturation coincidence** (lesson 5) that must never be quoted as
   parity. A full sweep is 25 + 75 pipeline runs.
4. **The ch10 rectifier** (Open item 2) — `resample_categorical` is verified to preserve the label set {0, 0.5, 1};
   the camera model is Appendix A.
5. **Three deliberate deviations on branches the book never reaches** (Open item 4): `colorbar_area_ticks` keeps one
   tick where MATLAB's `min:0:max` is empty (labelled `near` for that branch); `IceShapeEnhancement.fsd` is `None` for
   an ice-free image where MATLAB `hist([], 50)` returns `zeros(1,50)`/`1:50` (never compared, because the reference
   wrapper guards the tail — but `core.histogram.hist` itself **is** compared on both empty forms and is 0 px);
   `core.histogram.hist` raises for a scalar `n < 1` where MATLAB takes the `binwidth = Inf` branch.
6. **ch06's `polybool` start-vertex residual is still the only source of inexactness in the chapter** — it propagates

   parity on an identification map, feed MATLAB's own `seg`, as the `iceenh` references do.

   for non-uniform illumination, not homomorphic filtering. Do not attach it to §7.1/§7.2.

   MATLAB behaviour; if ch08 sees a multi-component label, the `cat(1, cen.Centroid)` semantics are the reference.
